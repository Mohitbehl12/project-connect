# App Store and Google Play: in-app subscriptions

The iPhone and Android apps sell Premium through Apple's and Google's own billing (both stores require it for
digital subscriptions). The website keeps Razorpay. Everything below is code-complete; it needs the store
accounts and these settings before it can take real money.

## How a purchase works

1. The app loads the store's prices for the product ids the server lists (`/api/billing/catalogue` → `options[].store`).
2. The member buys in the store's payment sheet. The purchase carries an account id so it can't be claimed
   by another account (Apple `appAccountToken` = the user's id; Google `obfuscatedAccountId` = a hash of it).
3. The app sends the purchase to `POST /api/billing/store/verify`. The server checks it with the store:
   - Apple: the StoreKit 2 signed transaction is verified against Apple's root certificates (official
     `@apple/app-store-server-library`).
   - Google: the server asks the Play Developer API for the subscription's real state.
4. Only after the server accepts it does the app finish the transaction. Unfinished ones retry on next launch.
5. Renewals, cancellations, grace periods and refunds arrive as store notifications and update the plan.

Cancelling and changing store plans happens in the store (the app links there). Account deletion tells the
member to cancel their store subscription, because deleting the account can't stop Apple or Google charging.

## Product ids (create these exactly, as auto-renewable subscriptions)

| Product id | Plan | Period | India price (set in the store) |
| --- | --- | --- | --- |
| `premium_1m` | Premium | 1 month | ₹50 |
| `premium_12m` | Premium | 1 year | ₹500 |
| `premium_men_1m` | Premium (men, India) | 1 month | ₹100 |
| `premium_men_3m` | Premium (men, India) | 3 months | ₹250 |
| `premium_men_6m` | Premium (men, India) | 6 months | ₹500 |
| `premium_men_12m` | Premium (men, India) | 1 year | ₹1,000 |
| `plus_1m`, `plus_men_1m` | Premium Plus | 1 month | ₹149 / ₹249 |
| `vip_1m`, `vip_men_1m` | VIP | 1 month | ₹599 / ₹999 |

Apple: put them all in ONE subscription group so members can't hold two at once. Google: one subscription per
id, each with one base plan of the matching period. Ids can be changed per price in Admin (database columns
`apple_product_id`, `google_product_id`). Stores only offer their own price points, so the store price may
differ slightly from the server's; the app always shows the store's price.

Open question: Apple may question showing different products by gender. If so, offer only the `premium_*`
products on iPhone (set the men's rows' `apple_product_id` to the standard ids).

## Server settings (Render → Environment)

| Variable | Value |
| --- | --- |
| `STORE_BILLING_ENABLED` | `true` once the products exist (until then iPhone shows "not available yet") |
| `APPLE_BUNDLE_ID` | the app's bundle id, e.g. `in.yourbrand.app` |
| `APPLE_APP_ID` | the numeric Apple ID from App Store Connect → App Information (needed for live purchases) |
| `APPLE_ROOT_CERTS_B64` | Apple Root CA G3 (and G2) as base64 DER, comma-separated — from apple.com/certificateauthority. Or commit the `.cer` files to `certs/apple/` |
| `GOOGLE_PACKAGE_NAME` | the Android package name |
| `GOOGLE_SERVICE_ACCOUNT_JSON_B64` | base64 of a Google Cloud service-account key that Play Console has given "View financial data" and "Manage orders and subscriptions" |
| `GOOGLE_RTDN_TOKEN` | generated by Render; also goes in the Pub/Sub push URL |

## Store notifications

- Apple: App Store Connect → the app → App Information → App Store Server Notifications → Version 2 →
  `https://<your domain>/api/billing/apple/notifications` (production and sandbox).
- Google: create a Pub/Sub topic, grant `google-play-developer-notifications@system.gserviceaccount.com`
  publish rights, set it in Play Console → Monetization setup, and add a push subscription to
  `https://<your domain>/api/billing/google/notifications?token=<GOOGLE_RTDN_TOKEN>`.

## Testing

- Store purchases need a development or TestFlight build (not Expo Go): `npx eas-cli build --profile development`.
- Apple: sandbox testers (App Store Connect → Users and Access → Sandbox). Google: license testers in Play Console.
- Automated: `tests/unit/stores.test.ts` checks the Apple signature verification with a test certificate chain;
  the E2E suite runs the whole flow with clearly labelled `mock:` tokens, accepted only where mock payments are on.
- Not yet tested against the live Apple and Google services (needs the accounts above).
